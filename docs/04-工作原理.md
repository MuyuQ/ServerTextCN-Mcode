# 04 · 工作原理

写给想读代码、想改代码的人。读这页之前建议先过一遍 [03-补译与贡献指南](03-补译与贡献指南.md) 的"词典格式"，了解 GREET/MENU 和公告规则长什么样。

> 目标客户端是 3.3.5a（Lua 5.1，无新版 API）。所有代码遵循一个总原则：**插件只做"显示层替换"，词典未命中一律原样透传**——任何内部错误最多表现为"没翻"，不会"翻错"，也不会影响服务器交互。

## 文件分工与加载顺序

`ServerTextCN_Mcode.toc` 决定加载顺序（后面的文件可以用前面定义的全局量）：

| 顺序 | 文件 | 职责 |
|---|---|---|
| 1 | `ServerTextCN_Mcode_Data.lua` | 窗口内置词典（纯数据）：`McodeSTCN_Data.GREET/MENU`、NPC 收敛索引、词典版本头 |
| 2 | `Core.lua` | 公共基础：全局命名空间 `McodeSTCN`、文本归一化、上下文采集、记录系统、存档初始化与迁移 |
| 3 | `Templates.lua` | 译文模板扫描与渲染（公告规则用的 `{占位}` 标记体系） |
| 4 | `Notifications.lua` | 屏幕漏译提示条（私有框体，避免借用会被重复统计的公告通道） |
| 5 | `Window.lua` | 窗口汉化：词典合并、四层匹配、占位符双向处理、界面钩子 |
| 6 | `AnnouncementRules.lua` | 公告词典：24 条战场规则 + 系统公告规则（正则 + 捕获校验 + 词典查值） |
| 7 | `Announcements.lua` | 公告接入：聊天过滤器、事件采集器、显示层钩子、旧插件冲突检测 |
| 8 | `Options.lua` | 设置界面（原生 Interface Options 三个页面）、记录页 UI、复制反馈 |
| 9 | `ServerTextCN_Mcode.lua` | 入口：事件注册、初始化调用、`/stcn` 命令 |

全部逻辑挂在全局命名空间 `McodeSTCN` 下（存档变量是 `McodeSTCN_DB`），不污染 `_G` 其他名字。

## 生命周期与事件时序

入口文件注册 6 个事件：`ADDON_LOADED`、`VARIABLES_LOADED`、`PLAYER_LOGIN`、`GOSSIP_CLOSED`、`QUEST_FINISHED`、`TRAINER_CLOSED`。

- **`VARIABLES_LOADED` / `PLAYER_LOGIN` 都会调用 `C.Initialize()`**——这是实测教训：部分 3.3.5 环境在插件文件执行完之后会整体替换存档表，只在文件加载时初始化一次会读到空表。两个事件都初始化，并靠 `ready` 标志与幂等迁移保证只生效一次。
- **窗口钩子尝试 `C.Window.TryHooks()`** 会在 `ADDON_LOADED`、`VARIABLES_LOADED`、`PLAYER_LOGIN` 以及文件加载完各自调用一次。原因：`hooksecurefunc` 的目标函数（如 `ClassTrainerFrame_Update`）在登录早期可能还不存在（LoD 插件、FrameXML 加载顺序差异），所以"能钩就钩，钩不到等下一个事件再试"。
- **公告安装 `C.Announcements.Install()`** 在 `PLAYER_LOGIN` 执行（需要聊天过滤器 API 与界面框体就绪）；之后每次 `ADDON_LOADED` 都会补试显示层钩子。
- `GOSSIP_CLOSED` / `QUEST_FINISHED` / `TRAINER_CLOSED` → `C.Window.Close()`：清空本次对话的"已见"去重表与控件映射，让下一次对话重新记录/提醒。
- `/stcn` 命令在 `ready` 为假（存档未加载或版本过高）时会拒绝执行并给出提示。

## 窗口汉化管线（Window.lua）

接入点（都在官方 FrameXML 函数上做安全钩）：

| 窗口 | 钩子目标 | 说明 |
|---|---|---|
| 训练师问候 | `ClassTrainerFrame_Update` → `GetTrainerGreetingText` | 训练师窗口每次刷新都会调用 |
| NPC 对话 + 菜单 | `GossipFrameUpdate`、`GossipFrameOptionsUpdate` → `GetGossipText`、`GossipTitleButton1..32` | 菜单按钮和任务标题按钮共用一套按钮 |
| 任务问候 | `QuestFrameGreetingPanel` 的 `OnShow` | XML `function=` 早绑定的面板用 `HookScript` 直挂；两种存在形式都做了兼容 |

### 一次翻译的完整路径

```text
钩子触发 → 取控件原文（getter 优先，取不到读控件当前文本并对照缓存）
        → C.Normalize 归一化（剥颜色码、$B→空格、4+ 连点→省略号、空白折叠）
        → 四层匹配，返回 (中文, 匹配方式, 词典键)
        → ExpandCN：译文里的 $n/$N/$c/$C/$r/$R/$g男:女;/$B 按玩家信息展开
        → C.WrapColor：若原文整行被 |c…|r 包裹，译文恢复同样的包裹
        → SetText 写回控件（菜单按钮替换后调用 GossipResize 重排宽度）
```

### 四层匹配（`W.LookupBuiltin`）

1. **全库精确**：`dict[normalized]` 直接命中；未命中再用小写索引（服务器措辞大小写漂移）；仍未命中做**占位符还原**——把实发文本里的角色名还原成 `$n`/`$N`（纯文本替换）、职业/种族词还原成 `$C`/`$c`/`$R`/`$r`（**词边界安全**替换，防止 "damage" 里的 "mage" 被误换）后再查。
2. **NPC 骨架精确**：用 NPC 名（中文）查 NPC 收敛索引得到该 NPC 的候选词条集合，把归一化文本去掉**所有标点和空白**（"骨架"）后与候选键的骨架比对，相等即命中。对付标点/空白级别的措辞漂移。
3. **NPC 相似度**：同一候选集合内做**带带宽限制的 Levenshtein 编辑距离**，相似度 ≥ **0.9** 才采用。带宽限制（|长度差|超过阈值直接判 0、内层循环只算对角线附近）让长句比对开销可控；每个"NPC+词典"的候选档案只构建一次并缓存。
4. **透传**：全部未命中 → 显示原文，按收集开关进入记录流程。

**任务标题按钮**（`type == "Available"/"Active"`）只走第 1 层——任务标题和菜单共用按钮，且任务标题本地化程度高，宽松匹配容易误翻。

### 缓存

- `W.cache`：`作用域+词组+归一化文本+是否精确模式 → 结果`，上限 1024 条，满了整体重置（取"够用的 LRU 平替"，代码注释有说明）。
- `W.profiles`：每个 NPC 的候选档案缓存；`PLAYER_INFO` 在 `ClearCache` 时一并失效。

## 公告管线（Announcements.lua + AnnouncementRules.lua）

公告与窗口不同：没有"控件文本"可改，只有事件流和显示调用。三条接入通道：

1. **聊天过滤器**（`ChatFrame_AddMessageEventFilter`）：对 `CHAT_MSG_BG_SYSTEM_NEUTRAL/ALLIANCE/HORDE`、`CHAT_MSG_SYSTEM`、`CHAT_MSG_RAID_BOSS_EMOTE/WHISPER` 注册过滤器，命中内置规则就返回 `(false, 译文, …)`——聊天窗口显示译文而不是原文。这是"事件→显示"的标准通道。
2. **事件采集器**：一个隐藏 Frame 注册同样的事件，**只负责记录**。聊天过滤器可能对每个聊天窗口各跑一次，而采集器只注册一处，避免同一条消息被重复计数。
3. **显示层钩子**（屏幕消息）：`RaidBossEmoteFrame` / `UIErrorsFrame` 的 `OnEvent` 脚本用 `WrapFrame` 包一层（先翻译再调原脚本）；`RaidNotice_AddMessage` 与 `UIErrorsFrame.AddMessage` 这两个**直接显示函数**再各包一层，覆盖不走事件、直接调显示函数的消息。直接显示调用没有可靠事件来源，只使用战场规则（`source == "bg"` 的 24 条），不做无来源收集。

**重入保护**：`A.inEvent` 计数器保证"我们自己注入的译文再次流经显示链时"不会被二次翻译或二次记录。

**首领消息格式化**：首领喊话/密语的原文带 `%s`，显示时要用 `CHAT_MSG_RAID_BOSS_*_GET` 前缀格式化出"某某说："。翻译结果如果**无法**被同一个格式化函数处理（例如译文把 `%s` 丢了），主动放弃翻译返回原文——宁可漏翻不可错翻。现场信息里会同时记录格式化前后的原文/译文。

**旧插件冲突**：`IsAddOnLoaded("Mcode_BGTextCN")` 为真时公告模块整体暂停（`C.announcementConflict`），设置页给出"停用旧版并重载"。合并版保留与旧版完全一致的 24 条规则顺序与行为，规则 ID 形如 `announcement:flag-pickup-player`。

**规则执行**（`AnnouncementRules.lua`）：`A.Normalize` 先归一化并补齐句尾标点（服务器实发 `!`/`.` 漂移）→ 正则捕获 → 每条规则的 `capture` 回调做**语义校验**（例如阵营词必须在词典里、时态必须是 `was`/`has been`）→ 捕获值经阵营/据点/战场名等小词典查中文 → `Templates.Render` 展开 `{占位}` → `WrapColor` 保留原文颜色包裹。任何一步不合就放弃该规则，继续尝试下一条。

## 记录系统（Core.lua）

- **身份键**：`模块\031词组\031作用域\031归一化原文`。作用域是 `id:NPC_ID`、`name:NPC名` 或 `*`（公告无 NPC）。同键只保留一条，重复出现累加 `count` 并刷新时间与现场。
- **去重**：`W.seen`（窗口）保证同一次对话内同一文本不重复记录/提醒；公告按真实事件计数（服务器重发同一文本算多次）。
- **命中即迁移**：一条 miss 被词典实际翻译后，从 miss 列表移除、进入 hits 列表；旧记录若只剩迁移残留字段（`legacy`/`history`）会如实标注。
- **收录判定 `C.IsEnglish`**：剥掉链接与纹理标记后，含 ASCII 字母、**不含 CJK 字节**才可能算"未汉化"；`" -VS- "` 竞技场动态列表、空串、纯中文一律不记录——防止已汉化文本被第二条钩子路径二次回流时被误记为漏译。
- **容量**：miss ≤ 300、hits ≤ 200（每模块），超限淘汰最久未出现者。
- **容错**：所有游戏 API 调用走 `C.Read`（pcall 包裹），API 缺失或报错按空值处理。

## 存档结构（McodeSTCN_DB，schema 4）

```text
McodeSTCN_DB = {
  schemaVersion = 4,
  enabled       = true,          -- 窗口汉化总开关
  debug         = false,         -- 窗口匹配调试日志
  windowCollect = true,          -- 窗口漏译收集
  misses  = { … },               -- 窗口未汉化记录（≤300）
  hits    = { … },               -- 窗口翻译留痕（≤200）
  announcements = {
    enabled = true,              -- 公告汉化总开关
    collect = true,              -- 公告漏译收集
    sources = { bg=true, system=true, boss=true, info=false },
    misses  = { … }, hits = { … },
  },
  ui = { window = {tab, query, offset}, announcements = {…}, lastModule },
}
```

`C.Initialize()` 负责**幂等迁移**：补默认值、按 schema 版本迁移列表、清理 3.0 时代的规则编辑器遗留字段（`rules`、`drafts` 等）、把更高版本存档标记为 `storageError`（拒读但不破坏，提示装回对应版本）。记录条目自带 `dictionaryVersion`（采集时的词典版本），反馈时能对上"当时词典里到底有没有这句"。

## 模板系统（Templates.lua）

公告规则的译文是模板：`{玩家名} {阵营} {据点} {战场} {数字} {文本} {职业} {种族}` 是规则捕获值；`$n/$N/$c/$C/$r/$R` 取玩家自身信息；`$B` 换行；`$g男:女;` 按角色性别二选一。`C.Scan` 先把模板切成"字面量 + 标记"序列（未知标记直接返回 nil，让调用方放弃渲染），`C.Render` 再逐段替换。窗口词典的译文占位符不走这套（由 `Window.ExpandCN` 直接展开），两者口径一致但互不依赖。

## 词典数据文件（ServerTextCN_Mcode_Data.lua）

- 文件头是版本块（`-- STCN DICTIONARY VERSION … -- END STCN DICTIONARY VERSION`）：`McodeSTCN_DictionaryInfo.version`（`年.月.日.修订号`）与 `contentHash`（**去掉版本块后、统一 LF 换行的文件主体的 SHA-256**）。
- 主体三张表：`McodeSTCN_Data.GREET`（问候 5,396 条）、`McodeSTCN_Data.MENU`（菜单 1,995 条）、`McodeSTCN_NPC` / `McodeSTCN_NPC_MENU`（中文 NPC 名 → 候选键列表，3,413 + 1,764 个名字）。
- `Window.lua` 里还有少量**种子词条**（工程虫洞目的地、训练师通用问候等），内置词条优先于数据文件——数据文件合并时只收录种子没有的键。
- 本仓库收录的是**生成产物**。维护工程用多语料管线（ID 锚定配对 + 人工增补 TSV + 变体表）生成该文件，并自动维护版本头；该管线依赖本地语料与汉化包数据，不属于本仓库。仓库内的增量通道是 `tools/add_dictionary_entries.py`（TSV → 词典，自动维护版本头）与人工回填（见 [03](03-补译与贡献指南.md)）。

## 已知边界（如实声明）

- 只翻译**插件已接入**的窗口与事件；任务标题、技能提示、物品浮层、玩家聊天等不在覆盖范围。
- 没有实时机器翻译，词典外文本原样显示。
- 服务器把占位符展开成具体值后（如实发 "Wcode!"），运行时只能还原有把握的词（角色名/职业/种族），无法从译文反推全部原始占位符。
- 相似度匹配只对**当前 NPC 的候选词条**进行，阈值 0.9 偏保守——这是"宁可漏翻、不可错翻"的取舍。
- 3.3.5 的全局词典无法按 NPC 区分同句异义；这类歧义键在收编时会被拦下讨论而不是强行收录。
